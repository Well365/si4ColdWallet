# P0 费曼汇报：范围与威胁模型

日期：2026-10-10

## 1. 一句话

在写第一行代码之前，先把"做什么、防谁、守哪些规矩"写成白纸黑字，以后任何人想偷懒破例，都要在文档里留下记录。

## 2. 讲给外行听

做一个保险箱，第一步不是买钢板，而是先想清楚三件事：

- **箱子里放什么**：种子（钥匙的母版），以及"你以为你签的就是你真正签的"。
- **贼是谁、会怎么来**：我们假设联网的那台手机已经被黑，网络会骗人，帮我们供货的零件商（第三方代码作者）会被收买，连我们自己人的账号也可能被盗。
- **只能信谁**：在 iPhone 上，苹果的系统和编译工具没法不信；Rust 官方编译器也没法不信。除此之外，谁都不信。

"不信零件商"具体是什么意思？平常大家装一个开源库，是从包仓库（像一个中转仓库）下载**打好包的成品**。这个成品不一定和作者公开的源码一样，中转仓库或作者账号被盗时，成品可能被换掉。所以我们的规矩是：**不要成品，只要源码**——直接去作者的 git 仓库，拿某一个固定版本（commit）的源码，整棵目录算出指纹（哈希）记下来。以后每次构建前重算一遍，指纹不对就停。构建时把网断掉，缺了任何东西就构建失败，而不是"顺手去网上下一个"。

本阶段相比上一版方案改了两个决定：

1. **不用 UniFFI，改为手写 C 接口（D2）**。UniFFI 会带进几十个在构建机上执行的依赖，和"尽量少让别人的代码在我们机器上跑"冲突。
2. **BIP39、UR 二维码编码自己写（D5）**。它们本质是"编码规则"而不是密码学算法，有官方测试向量可以逐条核对；椭圆曲线、哈希这类真正的密码学仍然用上游经过长期审查的源码，不自己写。

## 4. 怎么证明它是对的

P0 的产出是文档，"对不对"靠两点检验：

- 威胁清单里每一条都对应一个真实发生过的事件（见上一轮调研的来源），没有凭空想象的威胁。
- 每条规则都对应一个**可以自动执行的检查**（C1–C6），P1 会把这些检查写成脚本并实际跑通——到那时才算真正验证。目前：**未验证**。

## 5. 我讲不清 / 没把握的地方（知识缺口）

| 缺口 | 为什么讲不清 | 怎么补 | 何时补 |
|---|---|---|---|
| 开发者证书断网后能撑多久 | 苹果没有公开文档，论坛说法互相矛盾 | 真机实测 D1–D4（第 1/7/30/60/90 天） | P1 开始，持续 90 天 |
| iOS App 能否做到逐字节可复现 | Xcode 资源编译、代码签名会引入差异，社区经验少 | 两台 Mac 实际编译比对；先保证 Rust 静态库可复现 | P1 |
| Rust 编译器自身可信度 | rustc 自举依赖上一版二进制，理论上无法从零证明 | 锁版本 + 两地下载比对哈希 + 验证官方 GPG 签名；接受为信任根 | P1 |
| Keystone 各链解析代码能拆出多少 | 还没逐个读源码，不清楚和 cryptoxide 的耦合程度 | 逐链阅读，评估拷贝范围 | P2 每条链开始前 |
| ed25519、Keccak 用哪份上游源码 | 候选库的审计情况不完整（dalek 只有 2019 年审计） | 对比候选，记录决策 | P2 开始前 |

## 6. 和计划相比

- 计划 2 周，文档部分已完成。
- 待办（需要你本人）：准备 2 台 iPhone、Apple 付费开发者账号。没有真机，P1 的 D1–D4 实测无法开始。
- 当前这台 Mac 是日常用机。开发阶段可以用；**发布构建**必须换专用 Mac（规则 R2.4）。

## 7. 下一步（P1）

1. 在项目专用目录安装并锁定 Rust 工具链，验证官方哈希与 GPG 签名，记录到 `toolchain/TOOLCHAIN.lock`。
2. 写出 C1–C5 检查脚本，并让它们在空仓库上先跑通。
3. 按"上游 git 源码"规则引入第一批依赖（rust-secp256k1、rust-bitcoin 及其子依赖），编译出能在 iPhone 上跑的 Rust 静态库，跑通 BIP39 官方测试向量。
