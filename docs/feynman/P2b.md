# P2b 费曼汇报：严格的随机数生成 + 各链地址

日期：2026-10-10 · 状态：完成（按你的要求插队到 EIP-712 之前；EIP-712 已完成严格 JSON 解析器，其余暂停）

> 费曼法：如果不能用大白话讲给外行听懂，就说明自己还没真正弄懂。讲不清的地方，就是要补的缺口。

## 1. 一句话

签名机现在用两种方式生成助记词，并直接显示 BTC、ETH/BNB、SOL、DOGE、TRON、NEAR 六条链的收款地址：
- **混合模式**：系统随机数先体检，再与骰子混合。
- **纯骰子模式**：可以在别的电脑上独立验证。

每条链的地址都和一份完全独立写的程序算出来的结果逐字一致。

## 2. 讲给外行听

**为什么随机数是钱包的命根子**：助记词就是一个随机数。只要随机数有缺陷，比如只有 32 位真随机，或者被某个库"固定"了，攻击者就能把所有可能的钱包挨个算一遍。2023 年的 Milk Sad 事件就是这样，Libbitcoin `bx` 生成的钱包被批量盗空。

**两道保险**：
1. **给系统随机数"体检"**：真随机的 32 个字节，几乎不可能出现以下情况：
   - 只有十几种不同的值；
   - 5 个字节连着一样；
   - 排成等差数列；
   - 和上一次完全相同。

   出现任何一种，签名机就拒绝生成，并提示改用纯骰子。体检只能发现"坏掉的"随机数，证明不了"随机"——所以还有第二道保险。
2. **骰子**：每掷一次骰子提供约 2.6 位真随机。
   - **混合模式**：把骰子和系统随机数搅在一起，只要骰子够多，系统随机数再差也不怕。
   - **纯骰子模式**：完全不用手机的随机数。助记词 = 骰子点数串的 SHA-256。你可以在一台离线电脑上用一行命令复算，亲眼确认助记词来自你自己掷的骰子，而不是手机里的某个后门。

**同一组助记词，为什么能管这么多条链**：助记词先变成一颗"种子"，再按每条链公认的"路径"派生出各自的钥匙，就像同一把总钥匙按不同的编号配出各个房间的钥匙。各链的差别有三点：
- **路径不同**：BTC 是 84'，ETH 是 60'，SOL 是 501'……
- **曲线不同**：BTC、ETH、DOGE、TRON 用 secp256k1，SOL、NEAR 用 Ed25519。
- **地址的写法不同**：bc1…、0x…、D…、T…、Base58、十六进制。

我们按 Phantom、TronLink、NEAR 钱包等主流钱包的默认路径来派生，所以同一组助记词在这些钱包里能看到相同的地址。

**怎么知道地址算对了**：我另外用纯 Python（不依赖任何第三方库）从零写了一遍所有算法，和 Rust 代码没有任何共享。两边对同一组助记词算出的地址必须逐字相同。测试助记词的结果，还与钱包社区通用的公开结果一致。

## 4. 怎么证明它是对的

### 4.1 随机数

| 证据 | 结果 |
|---|---|
| 健康检查 | 全零、全相同、只有 15 种字节值、5 个连续相同字节、等差数列、与上次相同——全部拒绝；正常随机样本通过 |
| 纯骰子模式 | 一串 100 次的骰子 → 助记词首词 `piano nasty`；50 次（12 词）→ `trend humble`：与 `verify_dice.py`（Python hashlib）一致；49 次 / 99 次被拒 |
| 假骰子 | 同一个点数按 100 次、`123456` 循环、12 位周期循环、10 个以上连续相同、某一面明显偏多——全部拒绝（卡方检验、连续相同、周期三项检查，误报率约 1e-5 或更低）；签名机与 `verify_dice.py` 用同一套规则 |
| 解锁后清除 | 解锁成功后会话里的助记词与 passphrase 立即清除（测试核对：单词数变为 0，签名账户仍在） |
| 同一会话随机数重复 | 第二次用相同系统随机数生成被拒（随机数源卡住） |
| 链接探针（模拟器） | 卡住的系统随机数被拒、骰子不够被拒、周期骰子被拒、纯骰子生成成功 |

### 4.4 独立审查

| 审查 | 发现 | 处理 |
|---|---|---|
| 随机数与多链地址安全审查（代码阅读 + 运行测试 + 用 Python 复现健康检查算误报率） | **无 CRITICAL / HIGH**。确认：纯骰子模式不依赖设备随机数；熵截断正确、无偏；SLIP-10 与各链编码符合标准；健康检查每次误报约 6.5e-9。3 个 MEDIUM：① 纯骰子模式接受"假骰子"（同一个点数按 100 次也能生成，而这样的钱包可被猜到）；② 解锁后助记词与 passphrase 仍留在会话里（与界面上"永不保存"不符）；③ Swift 侧骰子数组在扩容、撤销、出错时留有副本。5 个 LOW：混合模式不强制骰子数量；验证工具接受非法词数、点数出现在命令行历史、`echo -n` 在 macOS sh 下出错；Ed25519 路径的栈清洗余量没有重新测；NEAR 注释把 Ledger 路径写错；第三方待人工审查 | ①②③ 全部修复并加测试（假骰子五种形态、解锁后清除）；验证工具改为从标准输入读点数、校验词数、同步质量检查，提示改用 `printf`；栈残留扫描加入"纯骰子生成"路径与 Ed25519 主私钥、Solana 私钥、骰子熵三种模式；NEAR 注释更正。混合模式不强制骰子是有意的设计（系统随机数是主来源），界面在骰子不足时明确提示"安全性主要依赖系统随机数" |
| 审查人另外指出 | 健康检查对 Milk Sad 这类"32 位种子的伪随机数生成器"无能为力：它的输出看起来完全随机，10 万个样本全部通过检查 | 这正是为什么我们把骰子作为真正的保险，而不把健康检查当成证明；已写入 D27 与第 5 节 |

## 5. 我讲不清 / 没把握的地方（知识缺口）

| 缺口 | 为什么讲不清 | 怎么补 | 何时补 |
|---|---|---|---|
| 系统随机数到底有多好 | 苹果 `SecRandomCopyBytes` 是黑箱；健康检查只能发现明显坏掉的情况，对"种子太小但输出看似随机"的生成器（Milk Sad 类）完全无效（审查实测 10 万个样本全部通过） | 用骰子（混合或纯骰子模式）；这是设计上的保险，不依赖对黑箱的信任 | 已提供 |
| 骰子是否公平、用户是否真的掷了 | 程序无法知道 | 界面提示用真实骰子；纯骰子模式下可以多掷（多于最低次数只会更安全） | 使用说明 |
| 真机上的生成与显示 | 只在模拟器验证 | 真机实测 | 需要你的设备 |
| Ed25519 链只能显示前 20 个账户 | 路径全部强化，不能由公钥派生；为了不在内存里保留额外的私钥，解锁时只预算前 20 个 | 签名功能实现时改为按需派生 | P2d |
| 第三方 ed25519-compact 人工审查 | 约 5500 行，待两名审查人 | 与其他第三方一起审查 | 需要审查人 |
