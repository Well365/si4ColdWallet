# P0 Feynman report: Scope and threat model

Date: 2026-10-10

## 1. In one sentence

Before writing the first line of code, we first put "what to build, whom to defend against, and which rules to follow" down in black and white, so that from now on anyone who wants to cut corners and make an exception has to leave a record of it in the documents.

## 2. Explained for a layperson

When you build a safe, the first step isn't buying steel plate; it's thinking three things through:

- **What goes in the safe**: the seed (the master copy of the keys), and the guarantee that "what you think you are signing is what you are really signing".
- **Who the thieves are and how they'll come**: we assume the internet-connected phone has already been hacked, the network will lie, the parts suppliers who supply us (third-party code authors) can be bought off, and even our own people's accounts may be stolen.
- **The only ones we trust**: on the iPhone, there's no way around trusting Apple's operating system and build tools; there's also no way around trusting the official Rust compiler. Beyond that, we trust no one.

What exactly does "not trusting the parts suppliers" mean? Normally, when people install an open-source library, they download a **pre-packaged finished product** from a package registry (something like a transit warehouse). That finished product isn't necessarily the same as the source code the author published; if the transit warehouse or the author's account is compromised, the finished product can be swapped out. So our rule is: **no finished products, source code only** — go straight to the author's git repository, take the source code of one fixed version (a commit), compute a fingerprint (hash) over the whole directory tree, and record it. Before every build from then on, recompute it, and stop if the fingerprint doesn't match. Cut off the network during builds, so that if anything is missing the build fails, rather than "just grabbing one from the internet along the way".

Compared with the previous version of the plan, this phase changed two decisions:

1. **No UniFFI; a hand-written C interface instead (D2)**. UniFFI would bring in dozens of dependencies that execute on the build machine, which conflicts with "let as little of other people's code as possible run on our machines".
2. **We write BIP39 and the UR QR code encoding ourselves (D5)**. At heart they are "encoding rules", not cryptographic algorithms, and they have official test vectors we can check one by one; real cryptography such as elliptic curves and hashing still uses upstream source code that has undergone long-term review, and we don't write it ourselves.

## 4. How we prove it is right

P0's output is documents, so "is it right" is tested on two points:

- Every item in the threat list corresponds to an event that really happened (see the sources from the previous round of research); there are no threats imagined out of thin air.
- Every rule corresponds to a **check that can be run automatically** (C1–C6); P1 will turn these checks into scripts and actually get them running — only then will they count as truly verified. For now: **not verified**.
