# P2b Feynman report: strict randomness generation + per-chain addresses

Date: 2026-10-10 · Status: complete (moved ahead of EIP-712 at your request; for EIP-712 the strict JSON parser is done and the rest is paused)

> The Feynman method: if you can't explain something in plain words so that a layperson understands it, you haven't truly understood it yourself. Wherever you can't explain clearly is a gap that needs filling.

## 1. In one sentence

The Signer now generates mnemonics in two ways, and directly displays receiving addresses for six chains (BTC, ETH/BNB, SOL, DOGE, TRON, NEAR):
- **Mixed mode**: the system randomness first gets a "check-up", then is mixed with dice.
- **Dice-only mode**: can be verified independently on another computer.

For every chain, the addresses match character for character the results computed by a completely independently written program.

## 2. Explained to a layperson

**Why randomness is a wallet's lifeblood**: a mnemonic is simply a random number. If that random number has any flaw — for example, only 32 bits of true randomness, or being "fixed" by some library — an attacker can compute every possible wallet one by one. That is exactly what happened in the 2023 Milk Sad incident: wallets generated by Libbitcoin `bx` were drained en masse.

**Two layers of insurance**:
1. **A "check-up" for the system randomness**: 32 truly random bytes will almost never show any of the following:
   - only a dozen or so distinct values;
   - 5 identical bytes in a row;
   - an arithmetic progression;
   - an exact repeat of the previous time.

   If any of these occurs, the Signer refuses to generate and suggests switching to dice-only. The check-up can only catch "broken" randomness; it can't prove "randomness" — which is why there is a second layer of insurance.
2. **Dice**: each dice roll provides about 2.6 bits of true randomness.
   - **Mixed mode**: the dice are stirred together with the system randomness; as long as there are enough dice rolls, it doesn't matter how bad the system randomness is.
   - **Dice-only mode**: the phone's randomness is not used at all. Mnemonic = SHA-256 of the string of dice values. You can recompute it on an offline computer with a one-line command and confirm with your own eyes that the mnemonic comes from the dice you rolled yourself, not from some backdoor in the phone.

**Why one mnemonic can manage so many chains**: the mnemonic is first turned into a "seed", and then each chain's own keys are derived from it along that chain's generally accepted "path" — just as the keys to the individual rooms are cut from the same master key according to different numbers. The chains differ in three ways:
- **Different paths**: BTC is 84', ETH is 60', SOL is 501'…
- **Different curves**: BTC, ETH, DOGE and TRON use secp256k1; SOL and NEAR use Ed25519.
- **Different address formats**: bc1…, 0x…, D…, T…, Base58, hexadecimal.

We derive along the default paths of mainstream wallets such as Phantom, TronLink and NEAR Wallet, so the same mnemonic shows the same addresses in those wallets.

**How do we know the addresses are computed correctly**: I separately wrote all the algorithms again from scratch in pure Python (with no third-party libraries at all), sharing nothing with the Rust code. For the same mnemonic, the addresses computed by the two sides must be identical character for character. For the test mnemonic, the results also match the public results commonly used in the wallet community.

## 4. How we prove it is correct

### 4.1 Randomness

| Evidence | Result |
|---|---|
| Health check | All zeros, all identical, only 15 distinct byte values, 5 consecutive identical bytes, arithmetic progression, same as last time — all rejected; normal random samples pass |
| Dice-only mode | A string of 100 rolls → mnemonic starting with `piano nasty`; 50 rolls (12 words) → `trend humble`: matches `verify_dice.py` (Python hashlib); 49 / 99 rolls are rejected |
| Fake dice | The same value entered 100 times, a repeating `123456` cycle, a repeating 12-digit cycle, 10 or more identical in a row, one face clearly over-represented — all rejected (three checks: chi-square test, identical runs, periodicity; false-positive rate about 1e-5 or lower); the Signer and `verify_dice.py` use the same set of rules |
| Cleared after unlock | After a successful unlock, the mnemonic and passphrase in the session are cleared immediately (checked by test: the word count becomes 0, while the signing accounts are still there) |
| Repeated randomness within one session | A second generation using the same system randomness is rejected (the randomness source is stuck) |
| Link probe (simulator) | Stuck system randomness rejected, too few dice rejected, periodic dice rejected, dice-only generation succeeds |

## 5. What I can't explain clearly / am not sure about (knowledge gaps)

| Gap | Why I can't explain it clearly | How to fill it | When to fill it |
|---|---|---|---|
| How good the system randomness really is | Apple's `SecRandomCopyBytes` is a black box; the health check can only detect obviously broken cases, and it is completely ineffective against generators whose "seed is too small but whose output looks random" (the Milk Sad kind) (in the review's measurements, all 100,000 samples passed) | Use dice (mixed or dice-only mode); this is insurance built into the design and does not depend on trusting the black box | Already provided |
| Whether the dice are fair, and whether the user really rolled them | The program has no way of knowing | The UI advises using real dice; in dice-only mode you can roll more times (more than the minimum only makes it safer) | Usage instructions |
| Generation and display on real devices | Verified only on the simulator | Test on real devices | Needs your devices |
| Ed25519 chains can only show the first 20 accounts | Every level of the path is hardened, so nothing can be derived from a public key; to avoid keeping extra private keys in memory, only the first 20 are precomputed at unlock | Switch to on-demand derivation when signing is implemented | P2d |
| Human review of the third-party ed25519-compact | About 5500 lines, awaiting two reviewers | Review it together with the other third-party code | Needs reviewers |

## 8. Addendum (2026-10-11): Solana gained an "account type"

After restoring a Ledger mnemonic, the Solana address differed from the one in Ledger Live — not a miscalculation, but **the same key walking a different road in a different wallet**. Ledger Live keeps three roads for Solana: `m/44'/501'` (the earliest main account), `m/44'/501'/index'`, and `m/44'/501'/index'/0'` (the same as Phantom and Trezor). The Signer used to walk only the last one. With SOL selected you can now switch between "Phantom / Trezor", "Ledger Live" and "Ledger main account"; all three addresses can be displayed and checked by QR, and each is cross-checked by the independent Python implementation (decision D34).
