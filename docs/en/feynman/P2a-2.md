# P2a part 2 Feynman report: EIP-712 structured-data signing, plus passphrase mode and block explorer URLs

Date: 2026-10-10 · Status: complete (verified on the simulator; not yet installed on real devices, which requires a developer account)

> The Feynman method: if you can't explain something in plain words so that a layperson understands it, you haven't truly understood it yourself. Wherever you can't explain clearly is a gap that needs filling.

## 1. In one sentence

The Signer can now understand "structured-data signing" (EIP-712): it lists every signed field in full, and always requires ticking a confirmation box before it signs. The Watcher can initiate this kind of signing request. In addition, two items were added at your request:
- **passphrase mode**: enter it twice; you can check it against an expected fingerprint, and if you enter it wrong you can't get in.
- **Block explorer URLs**: shown only as text on the Signer; clickable on the Watcher.

## 2. Explained to a layperson

**What structured-data signing is**: many websites don't ask you to send a transaction; instead they ask you to "sign a form". The form says "who, approving whom, for how much, until when". Once you have signed it, the other party can take this signature to the chain and "cash in" the approval or listing on your behalf. You don't have to sign any further transaction, and your money may already have been moved away. This has been the most common phishing technique of recent years:
- Permit, Permit2: off-chain approvals.
- Seaport: NFT listings, for example "sell me your NFT for 0".

**How the Signer defends against it**:
1. **Read the form strictly**:
   - A key appears twice in the form (JSON): refuse to sign.
   - One field too many or one field too few: refuse to sign.
   - A number outside its declared range: refuse to sign.
   - An address whose upper/lower-case checksum is wrong: refuse to sign.

   This guarantees that "what is shown on screen" and "what gets signed" are the same content.
2. **Show everything**: every field in the form is listed, with nothing truncated. A field that is too long (over 1024 bytes) can't be shown in full, so the Signer refuses to sign it outright, because not being able to see all of it is the same as blind signing.
3. **A summary for what it recognizes, a warning for what it doesn't**:
   - Recognized types: token Permit, DAI-style permit, the six Permit2 formats, and listings on Seaport's official contracts. The Signer spells out in Chinese "who is approved, for how much, when it expires", or "what you give, what you receive, who gets paid".
   - A listing in which you receive nothing, or in which everything you receive is something whose value can't be verified: a red warning.
   - Unrecognized types: it states plainly "the Signer doesn't understand this".
   - Recognized or not, signing always requires ticking the confirmation box. The confirmation requirement is written in Rust, so the UI can't bypass it.
4. **The chain must be right**: if the chain written in the form differs from the chain in the request, refuse to sign. If the form doesn't state a chain, it warns that "this signature can be used on any chain".

**passphrase mode**: a passphrase is like a 25th word. Its biggest pitfall: if you enter it wrong, you get no error; instead you quietly end up in a different, empty wallet, and you might then receive funds into that wallet. What we do now:
- When unlocking, you explicitly choose "passphrase wallet", and you must enter it twice, identically.
- You can fill in the 8-character "fingerprint" you noted down last time. The Signer checks the computed wallet fingerprint against it and won't let you in if they differ; the mnemonic is kept, so you only need to re-enter the passphrase.
- After unlocking, the top of every page shows "passphrase wallet · fingerprint xxxxxxxx", so you always know which wallet you are in.

**Block explorer URLs**: below an address, the Signer shows the URL on sites such as mempool.space and Etherscan. It is only text and can't be clicked, and the Signer contains no code at all that could open a URL. You can type it, as shown, into the browser of another, internet-connected device. The Watcher is online anyway, so there it gives you a link you can click directly.

## 4. How we prove it is correct

### 4.1 EIP-712

| Evidence | Result |
|---|---|
| Specification example (Mail) | Type hash, domain separator, message hash and final digest match the EIP-712 specification byte for byte; signing with the "cow" private key from the specification gives r / s / v identical to the specification |
| Independent Python implementation | Digests for 6 sets (including the MetaMask v4 array example, all basic types, Permit, Permit2, recursive types + salt) match byte for byte |
| The reviewer's boundary tests | Integer boundaries (20 points in total at ±1 for int256 / uint256 etc.), type-name ordering, mutual recursion, empty structs and other edge cases, 11 in all: all agree with the reference implementation |
| End-to-end | Permit via animated QR code (1 frame dropped out of every 3) → Signer reviews and signs → Watcher checks; an attempt to pass the same signature off as one for different data is caught |
| Signer C interface | Structured-data signing without ticking the confirmation → refuse to sign; with it ticked → signed, and the Watcher's check passes; chain ID mismatch → refuse to sign |
| Refusals to sign | Duplicate keys, extra fields, out-of-range values, non-UTF-8, addresses with a wrong checksum, non-canonical types such as `uint+8`, overlong fields, 65 types (returns immediately; similar data crafted during the review used to take more than 20 seconds to compute) |
| Recognition | Permit2 batch and witness, Permit2 with an unknown structure, fake Seaport contracts, listings where the amount you receive is 0, listings where you receive only NFTs, DAI approval revocation: all displayed and warned about as expected; every signed field has a corresponding display row, and all are high-risk |
| Simulator | Permit JSON pasted into the Watcher: it shows "Token Permit approval", unlimited amount, the approved party, expiry 2030-01-01, all fields and warnings; the animated QR code has 8 parts, and the frame numbers decoded from the screenshots increase; JSON garbled by the input method is rejected on the spot (screenshots in `build/screens/p2a2-*.png`) |
